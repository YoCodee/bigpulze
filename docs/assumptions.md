# Assumptions

Keputusan yang tidak diatur PRD secara eksplisit, dicatat agar bisa dilacak.

| Tanggal | Konteks | Keputusan |
|---|---|---|
| 2026-10-19 | **Ambiguitas #1 — Proteksi kolom `stock` pada tabel `products`.** RLS policy `products_write_owner FOR ALL` secara teknis memungkinkan owner mengubah kolom `stock` langsung tanpa melalui RPC, melanggar D6. | **Solusi:** Di `rls.sql`, hak `UPDATE` pada tabel `products` untuk role `authenticated` hanya diberikan pada kolom non-stok (`sku`, `name`, `category`, `cost_price`, `selling_price`, `min_stock_alert`, `aliases`, `is_active`, `updated_at`). Kolom `stock` tidak termasuk dalam `GRANT UPDATE`. RPC yang berjalan sebagai `SECURITY DEFINER` (pemilik fungsi = `postgres`) tetap bisa mengubah kolom `stock`. Stok awal produk baru = 0, diisi lewat RPC `restock_product`. Konsekuensi: policy `products_write_owner` dipecah menjadi `products_insert_owner` (INSERT) dan `products_delete_owner` (DELETE) terpisah; UPDATE dikontrol lewat column-level GRANT + RLS policy `products_update_owner`. |
| 2026-10-19 | **Fuzzy matching di voice parser (ambiguitas #3).** PRD §9.2 poin 6 menyebut "Dice coefficient pada trigram **atau** rasio Levenshtein" tanpa memilih. | Keputusan ditunda ke bagian D (Parser). Akan dipilih saat implementasi dan dicatat di sini. |
| 2026-10-19 | **Import produk dan stok awal.** PRD §8 template produk punya kolom `stok`. Keputusan ambiguitas #1 bilang stok awal = 0 diisi lewat restock. | RPC `import_products_batch` (SECURITY DEFINER) boleh menetapkan stok dari file CSV dan membuat `stock_movements` bertipe `IMPORT` karena ini operasi server terkontrol, bukan manipulasi klien ad-hoc. Untuk pembuatan produk manual (FR-1.3), stok tetap dimulai dari 0. |
| 2026-10-22 | **Horizon forecast pada fitur rekomendasi stok.** PRD §10.3 menetapkan horizon forecast 7 hari, sementara permintaan owner adalah melihat rekomendasi stok untuk 7 hari, 30 hari, maupun bulan depan. | Horizon diperluas ke tiga pilihan: `7d` (hari ini s.d. +6), `30d` (hari ini s.d. +29), dan `next_month` (hari ini s.d. akhir bulan depan, WIB). Perpanjangan memakai iterasi Holt-Winters yang sama (periode 7, α 0.3, β 0.05, γ 0.2) dan fallback yang sama (seasonal naive 7–20 hari, rata-rata bergerak < 7 hari). Rumus `target_stock = ceil(forecast_total) + min_stock_alert` dan `days_of_cover = stock / (forecast_total / horizon_days)` diterapkan terhadap periode yang dipilih, sehingga usulan restock untuk 30 hari/bulan depan secara proporsional lebih besar dari 7 hari (memang itu makna "menutup stok untuk periode tersebut"). Nilai untuk horizon > 7 hari berstatus estimasi dan ditampilkan sebagai such di UI. |
| 2026-10-22 | **Penyimpanan hasil forecast.** PRD §10.6 menetapkan orkestrasi `POST /api/ml/run-forecast` yang menulis tabel `forecasts` dan `ml_recommendations` dengan cache harian. | Rekomendasi stok dihitung **live** di `GET /api/stock/restock-recommendations`, mengikuti pola yang sudah dipakai `GET /api/stock/recommendations` (rekomendasi mutasi). Belum ada tabel `forecasts` yang ditulis dan endpoint `run-forecast` belum dibuat; keduanya tetap tersedia di PRD untuk pengembangan berikutnya. Alasan: memenuhi kebutuhan fitur dengan perubahan paling sedikit dan tanpa orkestrasi tambahan. |
| 2026-10-22 | **Jendela riwayat penjualan untuk analisis tren.** PRD §10.3 memakai "rentang dari tanggal transaksi pertama sampai kemarin" tanpa batas atas. | Pengambilan data dibatasi **90 hari terakhir** (termasuk kemarin) untuk menjaga performa query. Hari tanpa penjualan diisi 0. Deret mulai dari tanggal penjualan pertama produk tersebut, sehingga model dipilih otomatis: ≥ 21 hari → Holt-Winters, 7–20 hari → seasonal naive, < 7 hari → rata-rata bergerak. |
| 2026-10-22 | **Lokasi modul ML baru.** PRD §10 dan D2 menempatkan ML di `frontend/src/server/ml/`, sementara kode yang sudah ada (anomaly, transfer-recommender, finance) berada di `frontend/src/lib/`. | Modul baru (`forecast.ts`, `stock-planner.ts`) ditempatkan di `frontend/src/server/ml/` sesuai PRD. Kode lama tidak dipindahkan (aturan "jangan me-refaktor kode yang tidak terkait") sehingga untuk sementara ada dua lokasi modul analitik. |
| 2026-10-22 | **Item tanpa riwayat penjualan.** Tidak jelas apakah produk yang belum pernah terjual boleh mendapat rekomendasi stok. | Produk tanpa satu pun transaksi pada jendela 90 hari **tidak** masuk daftar rekomendasi (tidak ada kecepatan konsumsi yang bisa diprediksi) dan dihitung terpisah pada `summary.products_without_history` agar owner tahu produk mana yang belum punya data. |
| 2026-10-22 | **Hak akses endpoint rekomendasi stok.** PRD §4 memberi role Cashier akses "lihat" pada halaman `/stock`, sedangkan halaman `/stock` sendiri hanya untuk Owner. | `GET /api/stock/restock-recommendations` khusus **OWNER** (Cashier mendapat 403), karena analisis tren lintas cabang andal memuat seluruh cabang. Sama seperti halaman `/stock` yang dibungkus `RoleGuard allowedRoles={['OWNER']}`. |
| 2026-10-23 | **Struktur data demo untuk seeder.** Data demo yang ada hanya 2 cabang (Senopati, Sudirman) dan 5 SKU, sementara PRD §11.1 mensyaratkan "Kopi Senja" 3 cabang (Malioboro, Condongcatur, Bantul) + 12 produk dan skenario S1–S6 yang menyebut cabang-cabang tersebut. | Diputuskan (bersama pemilik) untuk **mengikuti PRD §11.1 penuh**: seeder me-reset data bisnis dan master data demo ke 3 cabang + 36 baris produk, menghapus cabang/produk lama, dan memindahkan profil kasir ke Malioboro sebelum cabang lama dihapus (check constraint `CASHIER → branch_id wajib terisi`). Konsekuensi: nama cabang & SKU pada seluruh tampilan demo berubah menjadi spesifikasi PRD. |
| 2026-10-23 | **Granularitas mutasi stok pada seed.** PRD §11.1 tidak menentukan apakah `stock_movements` diisi per transaksi atau rekap; pengukuran menunjukkan ±1.300 baris/detik untuk insert remote sehingga 7.386 baris per transaksi membuat seed mepet target < 15 detik. | Mutasi `SALE` direkap **per produk per hari** (1.080 baris) dengan catatan jujur "Rekap penjualan harian … (N unit)" dan `stock_after` dihitung berjalan dari total terjual sehingga konsisten dengan stok akhir. Dampak: durasi seed ~8–13 detik (target < 15 detik) dan deret log stok tetap 30 hari penuh. Per transaksi tidak diubah; transaksi nyata lewat POS tetap membuat mutasi per transaksi. |
| 2026-10-23 | **`created_at` transaksi seed & detektor transaksi ganda.** `detectDuplicateTransactions` membandingkan `created_at` dua transaksi cabang sama dengan selisih ≤ 60 detik; insert batch membuat seluruh `created_at` jatuh dalam hitungan detik sehingga memicu alarm palsu. | Seeder mengisi `created_at` = waktu penjualan (bukan waktu seed) dan memakai **slot menit genap** (selisih ≥ 2 menit antar transaksi pada cabang sama). Kombinasi ini membuat alarm duplikat mustahil berbunyi untuk data yang memang dibuat terpisah oleh seeder, tanpa mengubah perilaku detektor untuk transaksi nyata. |
| 2026-10-23 | **Penandaan anomali S1 oleh seeder.** Endpoint `/api/anomalies` menandai anomali hidup sebagai *resolved* bila `expenses.is_anomaly = false`, sehingga lonjakan Rp 850.000 dari seeder tidak muncul pada daftar anomali terbuka. | Seeder menulis `is_anomaly = true` beserta `anomaly_score` (z-score) dan `anomaly_reason` pada baris S1, dengan baseline kategori/cabang dihitung saat seed memakai format yang sama dengan detektor aplikasi — sehingga skenario S1 tampil langsung sebagai anomali terbuka tanpa memodifikasi logika deteksi. |
| 2026-10-23 | **Menampilkan WAPE agregat.** PRD §11.3 S5 mensyaratkan "WAPE tampil (target < 25%)", sementara WAPE awalnya hanya muncul di modal detail tiap produk. | `summary.avg_wape_pct` (rata-rata seluruh produk ber-riwayat) ditambahkan pada respons dan ditampilkan sebagai kartu metrik ke-5 "Akurasi Backtest (WAPE)" di panel. Pada data seed nilai rata-rata 11,2% (maksimum individu 19,1%); noise ±15% mengikuti PRD §11.1 persis. |
| 2026-10-23 | **Batas 1.000 baris PostgREST (`db-max-rows`) terhadap query agregat.** Proyek membatasi setiap SELECT pada 1.000 baris tanpa error, sehingga query besar terpotong diam-diam begitu volume data melewati batas itu (terbukti pada data seed: riwayat rekomendasi, laporan PnL, dan agregat omzet anomali). | Helper `frontend/src/lib/supabase/paginate.ts` (`fetchAllRows`) dipasang pada 4 query agregat yang terpapar (rekomendasi stok, rekomendasi mutasi, PnL, anomali omzet). **Keterbatasan yang dicatat:** `GET /api/expenses` (daftar tampilan) belum terpaginasi dan tetap akan membatasi maksimal 1.000 baris pada org besar; volume data demo 360 baris sehingga belum terpengaruh, perbaikannya membutuhkan paginasi di sisi UI. |
| 2026-10-29 | **Fitur Asisten AI di luar PRD.** PRD §5.2 tidak mencantumkan asisten LLM dan aturan kerja melarang fitur di luar PRD. | Fitur ditambahkan atas permintaan eksplisit pemilik proyek (bukan inisiatif agent) dengan batasan disetujui: read-only, halaman khusus `/asisten` khusus OWNER, riwayat tersimpan di Supabase, input suara ditunda ke fase lanjutan. Spesifikasi tabel dicatat di PRD §7.1.2. |
| 2026-10-29 | **Pola akses data LLM: tool-calling vs text-to-SQL.** Asisten butuh data live (stok, penghasilan, dll) dari database. | Dipilih **tool-calling**: LLM hanya memilih fungsi read-only terbatas (`get_pnl_summary`, `get_top_products`, dst) yang dijalankan server dengan JWT owner sehingga RLS tetap menegakkan multi-tenant, semua argumen divalidasi Zod, dan angka jawaban hanya boleh berasal dari hasil tool (anti-halusinasi di system prompt). SQL bebas hasil teks LLM ditolak karena berisiko lintas-org dan salah sintaks. |
| 2026-10-29 | **Provider & kuantitas LLM.** Pemilik memilih Google Gemini; kuantitas jawaban streaming perlu hemat biaya. | Gemini `gemini-2.5-flash` via REST `streamGenerateContent` (SSE) tanpa SDK (aturan D13, tanpa dependency baru), diatur `GEMINI_MODEL` (default), key via `GEMINI_API_KEY` server-only. Riwayat yang dikirim dibatasi 14 pesan terakhir dan maksimal 4 putaran tool per pertanyaan; rentang query maksimum 90 hari; jawaban dipangkas (top-10 produk/maks 25 item). |
| 2026-10-29 | **Rate limit endpoint chat.** Tidak ditentukan PRD. | Sliding window sederhana 20 pesan/menit per OWNER, in-memory per instance Next.js (tidak lintas instance — cukup sebagai pengaman loop; di Vercel pun tidak dibagikan antar fungsi). Bukan pelaporan akurat billing. |
| 2026-10-29 | **Fungsi `get_forecasts` dapat kosong.** Menurut asumsi 2026-10-22, tabel `forecasts` belum ditulis oleh pipeline yang ada. | Tool halus mengembalikan `forecasts: null` + pesan "Belum ada forecast di database..." sehingga asisten menjawab jujur dan menyarankan jalan alternatif; akan aktif otomatis saat pipeline forecast diamankan. |
| 2026-10-29 | **Tabel `anomalies` tidak ada di skema**, sementara `GET /api/briefing/morning` lama pernah membacanya. | Tool asisten **tidak** memakai tabel tersebut; rekomendasi/anomali diambil dari `ml_recommendations` (`is_resolved = false`) + `expenses.is_anomaly`, konsisten dengan `GET /api/anomalies`. |
| 2026-10-29 | **Format jawaban asisten.** Tidak ditentukan PRD. | Jawaban streaming dalam Markdown ringan (poin-poin) dirender sebagai teks `whitespace-pre-wrap` tanpa markdown parser; chip sumber-data menampilken nama tool yang dipakai (transparansi angka) — sesuai nada UI Bahasa Indonesia. |
| 2026-10-30 | **Restock gagal "Format ID produk tidak valid" pada data demo.** `makeUuid()` seeder lama mengisi nibble versi/varian UUID secara acak, sehingga ID produk demo gagal konkansi RFC 9562 UUID v4 yang diperiksa `z.string().uuid()` (zod 4), padahal Postgres menerima dan baris lolos ke DB. | Seeder diperbaiki menghasilkan UUID v4 kanonik (versi `4`, varian `8/9/a/b`; commit `fix: generate canonical v4 uuids in demo seeder`). Validator tidak dilonggarkan: boundary tetap ketat; data lama dibenarkan dengan re-seed demo. |
